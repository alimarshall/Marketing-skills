# Project handoffs

Use these records only to the extent needed by the assignment. Keep the user's existing filenames, tracker and tooling when suitable. This is a suggested information model, not a mandatory folder structure.

## Shared company brief

Record offering/category; buyer roles; relevant use cases; capabilities and limits with sources; voice; approved brand assets; actual UI references; image preferences; placements and CTA policy. Separate explicit rules from inferred conventions. Include source dates and unresolved conflicts. Keep the current brief in the authorized project, not in reusable skill files.

## Evidence and proof

Give each excerpt or result a stable source ID, link/location, speaker or source type, date, exact excerpt, context and interpretation. Retain conditions for metrics. Mark exact quote, paraphrase and synthesis distinctly. Track attribution/publication constraints where known. Qualitative recurrence is directional research, not quantified market demand or performance proof.

## Concept record

Preserve concept ID; buyer/use case; source IDs; tension; angle; product job; headline/supporting copy/caption; proof and qualification; visual route; actual UI states if used; placement; source assets; version and review status. Keep internal notes outside customer-facing artwork.

The handoff should answer why this angle is credible, what the product does, what the viewer should see and what remains unverified. A clever headline without this context is not ready for automatic production at scale.

For visual work, include the visual job and why the chosen treatment expresses the angle, following `ad-creative-direction/references/angle-to-visual.md` from that installed skill. For photographic work, also carry the photo brief, source/licence or generation record, asset ID, intended crops, copy/UI space, usage limits and acceptance status using its `references/photos.md`. Keep these linked to the concept rather than making a separate unconnected image collection. Production receives the supported UI sequence where relevant; review checks the finished scene and product state against the original promise.

## Feedback and version record

Map each decision to the concept or shared component, its scope and the resulting version. Distinguish a proposed revision from an applied and verified change. Preserve accepted variants. When a shared image is rejected, locate all active uses before marking the revision complete.

Keep source copy, editable artwork, rendered exports and the review surface aligned. If the toolchain is partly manual, record which outputs require regeneration rather than claiming synchronization.

## Typical paths

- **New campaign:** company context + buyer research → use-case/angle coverage → copy and optional proof/reference analysis → angle-to-visual guidance and treatment selection → photo guidance and brief when relevant → relevant UI stories → production and review against the angle.
- **Proof campaign:** verify outcomes + buyer relevance → scoped proof routes → creative treatment → exports/review.
- **UI ad revision:** existing brief + specific feedback → verify interface and completion states → adjust composition → regenerate affected assets/review.
- **Copy-only request:** current evidence and offering → distinct angles and copy; stop at the requested written deliverable.
- **Reference-led exploration:** inspect references → transferable principles → company/buyer-specific original directions; do not copy competitor claims.

These paths are examples, not fixed gates. Parallel independent reading is useful; dependent claims and production decisions must use the resolved evidence. Collaboration among skills does not imply delegation to subagents.
